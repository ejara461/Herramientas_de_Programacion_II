Parte 1 — Iteración y acumuladores

Lectura 1 — Por qué necesitamos un bucle

En la Clase 5 trajimos un solo registro con mysqli_fetch_assoc(), llamado una única vez. Eso sirve para mostrar una fila, pero tu tabla ya tiene varios registros. Para mostrarlos todos necesitamos repetir la misma llamada a mysqli_fetch_assoc() una vez por cada fila — eso es exactamente lo que hace un bucle while.

Lectura 2 — while + mysqli_fetch_assoc(): el patrón para recorrer un resultado

$resultado = mysqli_query($conexion, "SELECT * FROM contactos");

while ($fila = mysqli_fetch_assoc($resultado)) {
    echo $fila["nombreContacto"] . " - " . $fila["telefono"] . "\n";
}

Mientras queden filas por leer, mysqli_fetch_assoc() devuelve un arreglo asociativo con la fila siguiente — y un arreglo se evalúa como verdadero en PHP. Cuando ya no quedan más filas, la función devuelve null, que se evalúa como falso, y ahí el while se detiene solo. No hace falta contar de antemano cuántas filas hay: el propio resultado le avisa al bucle cuándo parar.

Lectura 3 — Acumuladores: contar, sumar y promediar dentro del bucle

$contador = 0;
$suma = 0;
while ($fila = mysqli_fetch_assoc($resultado)) {
    $contador++;
    $suma = $suma + $fila["vecesContactado"];
}
$promedio = $suma / $contador;
echo "Total: " . $contador . " - Suma: " . $suma . " - Promedio: " . round($promedio, 2);

Un acumulador es una variable que se inicializa antes del bucle y se va modificando dentro del bucle, una vez por cada vuelta. Si $contador = 0 estuviera dentro del while, se reiniciaría a 0 en cada vuelta y nunca acumularía nada. El promedio no se calcula dentro del bucle — se calcula después, dividiendo la suma final entre el contador final.

Ejercicio interactivo

Si escribes $contador = 0; dentro del while, justo antes de $contador++;, ¿qué valor tendrá $contador al terminar el bucle, sin importar cuántas filas haya?

Parte 2 — Formularios: $_POST, $_GET, isset

Lectura 4 — Por qué capturar datos en vez de escribirlos fijos en el código

Hasta ahora, todo lo que insertamos o consultamos en la base de datos lo escribiste tú mismo, fijo en el código PHP. Pero una aplicación real recibe datos de un usuario final que no sabe programar: alguien llena un formulario en el navegador y esos datos deben llegar al script PHP. Para eso existen las variables superglobales $_POST y $_GET, que PHP llena automáticamente con lo que el usuario envió.

Lectura 5 — Formularios HTML y $_POST

<form method="post" action="recibir.php">
  Nombre: <input type="text" name="nombreContacto">
  <button type="submit">Enviar</button>
</form>

<?php
// recibir.php
echo "Recibido: " . $_POST["nombreContacto"];
?>

El atributo name de cada campo del formulario es la llave con la que ese valor llega en $_POST del lado del servidor. Con method="post", los datos viajan dentro del cuerpo de la petición HTTP — no se ven en la URL del navegador. Esto es importante para datos que no deberían quedar visibles ni guardados en el historial del navegador.

Lectura 6 — $_GET: datos capturados desde la URL

<a href="ver.php?categoria=familia">Ver familia</a>

<?php
// ver.php
echo "Filtrando por: " . $_GET["categoria"];
?>

$_GET funciona igual que $_POST — PHP llena automáticamente un arreglo asociativo — pero los valores viajan como parte de la URL, después del signo ?, en pares nombre=valor. Por eso sí se ven en la barra de direcciones y quedan en el historial del navegador: son útiles para enlaces que filtran o comparten resultados, no para datos sensibles.

Lectura 6b — GET vs POST, una comparación más completa

Más allá de dónde viajan los datos, GET y POST están pensados en HTTP para cosas distintas. Esta tabla resume las diferencias que vas a encontrar si sigues trabajando con desarrollo web:

CaracterísticaGETPOST
Propósito principalSolicitar o leer datos del servidor, sin cambiar nada.Enviar datos al servidor para crear, modificar o procesar algo.
Ubicación de los datosEn la URL (después del ?).En el cuerpo de la petición HTTP, no en la URL.
VisibilidadBaja: quedan en la URL, el historial del navegador y los registros (logs) del servidor.Media: no aparecen en la URL ni en el historial, pero no van cifrados por eso — sin HTTPS, cualquiera que intercepte la conexión los puede leer igual que los de GET.
Límite prácticoSí — la URL tiene un largo máximo (unos 2000 caracteres según el navegador).No hay un límite práctico — sirve para archivos y formularios grandes.
Repetir la peticiónSegura de repetir: recargar o volver a abrir el enlace no cambia nada en el servidor.No es segura de repetir: reenviar el mismo formulario puede duplicar una acción (por eso el navegador te pregunta antes de reenviar un POST).
Caché del navegadorEl navegador puede guardarla en caché por defecto.No se guarda en caché por defecto.

Relación con CRUD: GET corresponde al Read (R) — leer sin cambiar nada. POST corresponde a Create, Update y Delete (CUD) — las tres, no solo crear. La razón por la que Update y Delete también van por POST y no por algo más específico es simple: un formulario HTML (<form method="...">) solo acepta get o post como valor — no existe method="put" ni method="delete" en HTML. Distinguir un INSERT de un UPDATE o un DELETE es trabajo del script PHP (qué sentencia SQL ejecuta), no del método HTTP.

La excepción que hay que conocer: no todo Read va por GET. La regla completa es: usa GET para un Read solo si el valor que filtras no es sensible y no hay problema en que quede en la URL, el historial del navegador y los logs del servidor — como categoria o tipoMantenimiento en el Ejercicio 6, valores públicos sin riesgo. Si el valor que necesitas para leer sí es sensible — un número de documento de identidad, una contraseña, cualquier dato personal — usa POST aunque sea técnicamente un Read, precisamente para que no quede expuesto donde no debería. Por eso, por ejemplo, nunca se construye una búsqueda de estudiante por documento con buscar.php?documento=1234567: aunque sea solo una consulta, el documento quedaría visible en la URL y en el historial — algo que choca directo con la Ley 1581 de 2012 que ya rige todo el manejo de datos de este curso.

Nota práctica — por qué el navegador te advierte al recargar un formulario enviado

La fila "Repetir la petición" de la tabla anterior no es solo teoría: es justo lo que hace tu propio navegador cuando, después de enviar un formulario por $_POST, presionas F5 o el botón de recargar. En vez de reenviarlo sin más, el navegador muestra un aviso del estilo "¿Deseas reenviar el formulario?" — precisamente porque un POST repetido podría duplicar una acción. Con un enlace GET (como los del Ejercicio 6), recargar la página nunca muestra ese aviso: volver a pedir los mismos datos no tiene ningún efecto secundario.

Lectura 7 — isset(): verificar que un dato llegó antes de usarlo

<?php
if (isset($_POST["nombreContacto"])) {
    echo "Hola, " . $_POST["nombreContacto"];
} else {
    echo "Falta el nombre en el formulario.";
}
?>

Si el script intenta leer $_POST["nombreContacto"] pero ese campo no llegó (por ejemplo, porque el formulario no se envió completo, o alguien accede al script directamente sin pasar por el formulario), PHP genera un aviso de índice no definido ("undefined array key") y trata el valor como vacío — el script sigue corriendo, pero con un aviso molesto y un comportamiento posiblemente incorrecto. isset() comprueba si una variable existe y no es null antes de usarla, evitando ese aviso.
