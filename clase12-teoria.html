Clase 12 · Editar y eliminar registros (UPDATE y DELETE)

Formulario de edición precargado, UPDATE, DELETE con confirmación y páginas protegidas — 1:00 p. m. a 5:30 p. m.

Parte 1 — Completar el CRUD

Lectura 1 — Las cuatro operaciones

Una aplicación que maneja datos necesita cuatro operaciones, que se conocen con la sigla CRUD: Crear (INSERT, Clase 8), leer o consultar (SELECT, Clases 5 y 7), actualizar (UPDATE) y borrar (DELETE). Hoy completas las dos que faltan.

Las dos trabajan sobre un solo registro, el que la persona eligió en el listado. Para saber cuál es, se usa su id: la llave primaria que MySQL asignó al insertarlo y que nunca se repite. Todo lo de hoy se construye sobre el panel.php protegido de la Clase 11.

Parte 2 — Editar con UPDATE

Lectura 2 — La sentencia UPDATE

UPDATE repaso_mantenimientos
SET horasInvertidas = 7.5, completado = 1
WHERE id = 2;

SET indica qué columnas cambian y su valor nuevo, separadas por comas; las columnas que no aparecen en el SET no se tocan. WHERE indica cuáles registros cambian. Como id es la llave primaria, WHERE id = 2 afecta como máximo un registro.

Igual que en el INSERT, los textos van entre comillas simples y los números sin comillas.

Ejercicio interactivo

¿Cuál sentencia cambia el tipo del mantenimiento con id 4 a 'preventivo', sin tocar los demás registros?

Advertencia — UPDATE o DELETE sin WHERE

Un UPDATE sin WHERE modifica TODOS los registros de la tabla. Un DELETE sin WHERE BORRA TODOS los registros de la tabla.

MySQL no pregunta, no avisa y no tiene papelera de reciclaje: la sentencia se ejecuta en el instante y no se puede deshacer. Se comprobó sobre una copia de la tabla del tablero, con 6 registros: UPDATE copia SET equipo = 'Compresor de aire' dejó los 6 equipos con el mismo nombre, y DELETE FROM copia dejó la tabla vacía. Los datos anteriores se perdieron.

En una empresa, este error es borrar el inventario completo, cambiarle el precio a todos los productos o eliminar la historia de todos los clientes, con una sola línea. No es un error de principiante que "le pasa a otros": ocurre por un WHERE olvidado, mal escrito o con una variable vacía.

Regla sin excepciones: antes de ejecutar cualquier UPDATE o DELETE (en PHP o en phpMyAdmin), lee la sentencia completa y busca el WHERE. Si no está, no la ejecutes. Si dudas, escribe primero un SELECT con el mismo WHERE y mira cuántas filas devuelve: esas son las que vas a modificar o borrar. En esta clase no se practica un UPDATE ni un DELETE sin WHERE.

Ejercicio interactivo

Alguien ejecuta en phpMyAdmin DELETE FROM repaso_mantenimientos; (sin WHERE). ¿Qué pasa?

Lectura 3 — ¿Cuál registro se edita? El id viaja por POST

En el panel, cada fila tiene un pequeño formulario method="post" con el id de ese registro en un campo oculto y un botón. Al presionar Editar, el id llega a editar.php en $_POST["id"], igual que los datos de los formularios de la Clase 8:

<form method="post" action="editar.php">
  <input type="hidden" name="id" value="<?php echo $fila["id"]; ?>">
  <button type="submit">Editar</button>
</form>

action="editar.php" indica a qué página se envía. Todo lo que llega por un formulario es texto: aunque el campo oculto tenga value="2", $_POST["id"] vale "2" (una cadena). Además, quien envía el formulario puede alterar ese valor (Lectura 10). Por eso en editar.php el id se recibe con (int), que lo convierte a número entero: si no empieza por un número, queda en 0, y en el SQL solo puede entrar un número.

$id = 0;
if (isset($_POST["id"])) {
    $id = (int)$_POST["id"];
}
$resultado = mysqli_query($conexion, "SELECT * FROM repaso_mantenimientos WHERE id = $id");
$fila = mysqli_fetch_assoc($resultado);

Lectura 4 — El formulario precargado y el campo oculto

Para editar, el formulario debe aparecer lleno con los valores actuales, para que la persona cambie solo lo que necesita. Cada tipo de campo se llena de una forma distinta:

<!-- Texto y número: atributo value -->
<input type="text" name="equipo" value="<?php echo $fila["equipo"]; ?>">

<!-- Lista: selected en la opción que coincide con el valor guardado -->
<option value="preventivo" <?php if ($fila["tipoMantenimiento"] === "preventivo") { echo "selected"; } ?>>preventivo</option>

<!-- Casilla: checked si en la tabla hay un 1 -->
<input type="checkbox" name="completado" value="1" <?php if ($fila["completado"] == 1) { echo "checked"; } ?>>

<!-- Campo oculto: lleva el id del registro cuando se envía el formulario -->
<input type="hidden" name="id" value="<?php echo $fila["id"]; ?>">

El campo type="hidden" no se ve en la página, pero viaja con el formulario. El formulario se envía a otro archivo, actualizar.php, igual que formulario.html enviaba a insertar.php en la Clase 8:

<form method="post" action="actualizar.php">
  <input type="hidden" name="id" value="<?php echo $fila["id"]; ?>">
  <!-- ... campos precargados ... -->
  <button type="submit" name="guardar">Guardar cambios</button>
</form>

Cuando la persona presiona Guardar, el id llega a actualizar.php en $_POST["id"] y así el UPDATE sabe, en su WHERE, cuál registro modificar.

Ejercicio interactivo

Lectura 5 — Guardar los cambios

Al presionar Guardar, actualizar.php repite el cuidado del INSERT de la Clase 8: validar campos vacíos con trim(), escapar los textos con mysqli_real_escape_string(), convertir los números con (int) o (float) y la casilla con isset(...) ? 1 : 0. Lo nuevo es la sentencia, con el id que llegó por el campo oculto:

if (isset($_POST["id"])) {
    $id = (int)$_POST["id"];
}
$sql = "UPDATE repaso_mantenimientos
        SET equipo = '$equipoSeguro', tipoMantenimiento = '$tipoSeguro',
            completado = $completado, horasInvertidas = $horasNum, costoEstimado = $costoNum
        WHERE id = $id";
mysqli_query($conexion, $sql);

Antes de ejecutarla, aplica la regla de la advertencia: ¿tiene WHERE?

Si algún campo llega vacío, actualizar.php no guarda nada: muestra "Todos los campos son obligatorios. No se modificó nada." y un botón que reabre editar.php con el mismo id, por POST:

<form method="post" action="editar.php">
  <input type="hidden" name="id" value="<?php echo $id; ?>">
  <button type="submit">Volver a editar</button>
</form>

Lectura 6 — ¿Cuántas filas cambiaron? mysqli_affected_rows()

echo "Filas modificadas: " . mysqli_affected_rows($conexion);

mysqli_affected_rows() devuelve cuántas filas cambió la última sentencia UPDATE o DELETE. Si editas un registro y cambias algo, devuelve 1. Si presionas Guardar sin cambiar nada, devuelve 0: MySQL no cuenta una fila como modificada cuando los valores nuevos son iguales a los que ya tenía. Las dos situaciones se comprobaron con el código del tablero.

Ejercicio interactivo

Abres un registro en editar.php y presionas Guardar sin cambiar ningún campo. ¿Qué devuelve mysqli_affected_rows($conexion)?

Lectura 7 — Un archivo muestra, otro procesa

Editar queda repartido en dos archivos, cada uno con una sola tarea, en el mismo orden en que ocurren las cosas:

editar.php       1. trae el registro y valida que exista
                 2. muestra el formulario precargado      ──(Guardar)──►

actualizar.php   3. valida el id y los campos
                 4. hace el UPDATE ... WHERE id
                 5. muestra el resultado (o, al final, vuelve al panel con un aviso)

Dentro de cada archivo se cumple otra regla: primero procesar, después mostrar. PHP ejecuta el archivo de arriba hacia abajo y va enviando el HTML al navegador a medida que lo encuentra. Por eso el PHP que recibe datos, consulta, guarda o redirige va arriba, y el HTML de abajo solo imprime variables ya calculadas. Si en actualizar.php el bloque que guarda quedara debajo del HTML, $mensaje no existiría cuando se imprime (aviso Warning: Undefined variable) y header("Location: ...") fallaría con el aviso headers already sent, igual que session_start() en la Clase 11. Es el mismo orden de insertar.php (Clase 8) y de login.php (Clase 11).

Eliminar sigue el mismo patrón (Lectura 9): eliminar.php muestra la confirmación y borrar.php hace el DELETE.

Parte 3 — Eliminar con DELETE y confirmación

Lectura 8 — La sentencia DELETE

DELETE FROM repaso_mantenimientos WHERE id = 6;

DELETE FROM borra filas completas (no columnas sueltas), y WHERE indica cuáles. Con WHERE id = 6 se borra solo ese registro. Sin WHERE se borra la tabla entera: vuelve a leer la advertencia de la Parte 2.

Lectura 9 — Por qué se pide confirmación antes de borrar

Un clic se da por error con facilidad, y el borrado no tiene vuelta atrás. Por eso el botón Eliminar del panel no borra: solo abre eliminar.php, una página de confirmación que muestra los datos del registro y pregunta. "Sí, eliminar" envía el formulario a borrar.php, que es el único archivo que ejecuta el DELETE. "Cancelar" es un enlace que vuelve al panel sin borrar nada.

Como seguro adicional, borrar.php solo borra si llega el botón con name="eliminar": si alguien abre ese archivo de otra forma, no se elimina nada.

<!-- en eliminar.php -->
<form method="post" action="borrar.php">
  <input type="hidden" name="id" value="<?php echo $fila["id"]; ?>">
  <button type="submit" name="eliminar">Sí, eliminar</button>
  <a href="panel.php">Cancelar</a>
</form>
// en borrar.php
if (isset($_POST["eliminar"])) {
    mysqli_query($conexion, "DELETE FROM repaso_mantenimientos WHERE id = $id");
}

Lectura 10 — Validar el id

Un campo oculto no se ve, pero no es seguro: con F12 (Inspeccionar elemento) cualquiera puede cambiar su valor a 9999 o a "abc" antes de presionar el botón. También se puede escribir a mano la dirección editar.php o actualizar.php sin pasar por el panel, y entonces no llega ningún id. En esos casos el SELECT no encuentra nada, mysqli_fetch_assoc() devuelve null y PHP muestra avisos (Warning) con un formulario vacío. Para evitarlo, se revisa que haya exactamente un registro antes de usarlo:

if (mysqli_num_rows($resultado) !== 1) {
    echo "<p>Registro no encontrado.</p>";
    echo "<p><a href=\"panel.php\">Volver al listado</a></p>";
    exit;
}
$fila = mysqli_fetch_assoc($resultado);

La misma validación va en los cuatro archivos: en editar.php y eliminar.php, para no mostrar un formulario o una confirmación de algo que no existe; en actualizar.php y borrar.php, antes del UPDATE y del DELETE, para no intentar modificar o borrar un registro que no existe.

Parte 4 — Proteger y avisar

Lectura 11 — Proteger los cuatro archivos

El bloque de sesión de la Clase 11 debe ir al inicio de cada página que solo deben usar personas autenticadas. Si panel.php está protegido pero editar.php, actualizar.php, eliminar.php o borrar.php no, cualquiera que conozca la dirección puede modificar o borrar registros sin iniciar sesión: es peor que solo ver el listado.

<?php
session_start();
if (!isset($_SESSION["usuario"])) {
    header("Location: login.php");
    exit;
}

Con este bloque, un formulario de borrado enviado sin sesión tampoco borra nada: el script se detiene en el exit antes de llegar al DELETE.

Lectura 12 — Volver al listado con un aviso

Después de guardar o borrar, lo normal es volver al listado y mostrar qué pasó. Se usa header() con un dato en la dirección, que el panel lee con $_GET:

// en actualizar.php, después del UPDATE
header("Location: panel.php?msg=actualizado&filas=" . mysqli_affected_rows($conexion));
exit;

// en borrar.php, después del DELETE
header("Location: panel.php?msg=eliminado");
exit;
// en panel.php
$aviso = "";
if (isset($_GET["msg"])) {
    if ($_GET["msg"] === "actualizado") {
        $aviso = "Registro actualizado.";
    } elseif ($_GET["msg"] === "eliminado") {
        $aviso = "Registro eliminado.";
    }
}

El panel compara $_GET["msg"] contra textos fijos y muestra un texto propio. Nunca imprimas directamente lo que llega en $_GET: cualquiera puede escribir lo que quiera en la dirección. Además, si la persona recarga el panel, no se repite el UPDATE ni el DELETE, porque el navegador ya está en panel.php y no en el formulario.

¿Por qué aquí sí se usa GET? La regla es: POST para enviar datos que modifican la base (insertar, editar, borrar) y GET para pedir o mostrar algo sin cambiar nada. El msg no modifica ningún registro: solo le dice al panel qué aviso mostrar. Si alguien recarga la página, guarda la dirección o la escribe a mano, lo peor que pasa es que vea un aviso. Por eso el id para editar y eliminar viaja por POST, y el aviso por GET. Además, header("Location: ...") siempre hace que el navegador abra la página nueva con GET, así que es la forma natural de pasarle ese dato.

Para conocer: en JavaScript existe confirm(), que muestra un cuadro de "Aceptar / Cancelar" en el navegador. Se verá con los eventos en la Clase 14. No reemplaza la página de confirmación: la decisión de borrar debe pasar por el servidor.
