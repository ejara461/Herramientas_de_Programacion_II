CSS responsivo, Bootstrap y arquitectura cliente-servidor

En la Clase 1 se auditó y corrigió el marcado semántico de la página de cada proyecto PIA. Esa página ya tiene estructura correcta, pero hoy toca revisar cómo se ve en distintos tamaños de pantalla y cómo encaja dentro del esquema completo de una aplicación web: navegador, servidor y base de datos. Ese esquema es el que se va a usar durante todo el módulo, desde la primera página en PHP (Clase 3) hasta el CRUD final contra MySQL.

1. Repaso rápido: el modelo de caja

Todo elemento HTML se renderiza como una caja rectangular compuesta, de adentro hacia afuera, por content, padding, border y margin. Por defecto, width y height solo fijan el tamaño del contenido: si se agrega padding o borde, la caja crece más allá de ese valor. Esto rompe diseños cuando se combinan anchos en porcentaje con padding en píxeles.

La corrección estándar, y la que se usa en todos los proyectos PIA de este curso, es box-sizing: border-box; aplicado globalmente. Con esa propiedad, width y height incluyen padding y borde, así que un elemento con width: 100% nunca se desborda de su contenedor sin importar el padding que se le agregue después.

*{
  box-sizing: border-box;
}

2. Diseño responsivo y media queries

Un diseño es responsivo cuando la misma página se adapta a distintos anchos de pantalla sin perder legibilidad ni funcionalidad: el menú de un proyecto PIA que se ve como barra horizontal en un computador de escritorio debe poder colapsar en un menú vertical o un botón en un celular, sin que el estudiante tenga que mantener dos versiones distintas del sitio.

La herramienta base para lograrlo son las media queries: bloques de CSS que solo aplican cuando se cumple una condición sobre el ancho de la ventana. La práctica recomendada es mobile-first: se escriben primero los estilos para pantalla pequeña como estilos por defecto, y luego se usan media queries con min-width para ir agregando estilos a medida que la pantalla crece. Es el orden contrario a escribir primero el diseño de escritorio y luego "apretar" para celular, y en la práctica produce hojas de estilo más cortas y más fáciles de mantener.

/* Estilos base: pensados para celular */
.tarjeta{ width: 100%; }

/* A partir de 768px (tablet en adelante) */
@media (min-width: 768px){
  .tarjeta{ width: 48%; }
}

/* A partir de 1024px (escritorio) */
@media (min-width: 1024px){
  .tarjeta{ width: 31%; }
}

3. Bootstrap: por qué se usa y qué resuelve

Bootstrap es una biblioteca de CSS (y JavaScript) que ya trae resuelto el trabajo repetitivo de un diseño responsivo: una rejilla de 12 columnas, componentes visuales comunes (botones, tarjetas, barras de navegación, alertas) y un conjunto de utilidades de espaciado. No reemplaza el CSS propio del proyecto, pero evita reescribir desde cero cosas como "que estas tres tarjetas se acomoden en una sola columna en celular y en tres columnas en escritorio".

Su pieza central es el sistema de rejilla: un .container que envuelve un .row, y dentro de la fila, columnas con clases como col-12 (ancho completo, 12 de 12 columnas) o col-md-6 (la mitad del ancho, mismo comportamiento que las media queries de la sección anterior, ya escrito por Bootstrap). El prefijo indica el punto de quiebre: sin prefijo aplica siempre; md, lg y xl aplican desde tablet, escritorio y pantallas grandes en adelante.

<div class="container">
  <div class="row">
    <div class="col-12 col-md-6 col-lg-4">Tarjeta 1</div>
    <div class="col-12 col-md-6 col-lg-4">Tarjeta 2</div>
    <div class="col-12 col-md-6 col-lg-4">Tarjeta 3</div>
  </div>
</div>
Regla práctica: antes de escribir una media query propia para un problema de columnas o de espaciado, revisar si Bootstrap ya trae una clase que lo resuelve (col-*, d-flex, m-*/p-*). Escribir CSS propio cuando ya existe una utilidad de Bootstrap duplica trabajo y es más difícil de mantener.

4. La arquitectura cliente-servidor

Hasta la Clase 1, cada proyecto PIA era un conjunto de archivos HTML, CSS y JavaScript que el navegador abre directamente desde el disco: no hay ningún programa del lado del servidor involucrado. Desde la Clase 3 eso cambia: se agrega PHP, un lenguaje que no corre en el navegador del estudiante sino en un servidor web (Apache, dentro de XAMPP), y desde la sesión 7 ese servidor además consulta una base de datos MySQL.

El flujo básico de una solicitud es siempre el mismo, sin importar qué tan compleja sea la página: el navegador (cliente) pide una página al servidor; si esa página es un .php, Apache la pasa al intérprete de PHP antes de responder; si el script PHP necesita datos, se conecta a MySQL, ejecuta una consulta y arma la página con esos datos; el servidor devuelve HTML ya terminado, y el navegador solo tiene que mostrarlo. El navegador nunca ve el código PHP ni se conecta directamente a la base de datos.

Navegador (cliente): HTML + CSS + JS, hace la solicitud
Servidor web (Apache): recibe la solicitud
Intérprete PHP: ejecuta el script, arma la consulta si hace falta
MySQL: responde los datos solicitados
Apache devuelve HTML final al navegador

Esta separación es la razón por la que el mismo proyecto de Gestión de Biblioteca, por ejemplo, podrá mostrar en pantalla el listado real de libros guardados en MySQL a partir de la sesión 8, sin que el HTML tenga que escribirse a mano fila por fila: el servidor genera ese HTML en el momento, con los datos que haya en la base en ese instante.

5. XAMPP: verificación, no instalación

XAMPP ya quedó instalado y confirmado funcionando desde el módulo de Bases de Datos: incluye Apache (el servidor web), MySQL (el motor de base de datos) y phpMyAdmin (la interfaz para administrar la base desde el navegador). Hoy no se instala nada nuevo: se verifica que los tres siguen arrancando correctamente en el equipo de cada estudiante, porque a partir de la Clase 3 el proyecto deja de funcionar si Apache o MySQL no están corriendo.

Verificación mínima antes de cerrar la sesión: abrir el panel de control de XAMPP, iniciar Apache y MySQL (ambos deben quedar en verde, sin mensaje de error de puerto ocupado), y entrar a localhost/phpmyadmin en el navegador para confirmar que la base de datos del proyecto PIA sigue ahí, tal como quedó al cierre del módulo de Bases de Datos.

Si un puerto aparece ocupado (típicamente el 80 de Apache, en conflicto con Skype u otro servicio), no se reinstala XAMPP: se cambia el puerto de Apache en su archivo de configuración o se cierra el programa que lo está usando. Documentar el caso puntual en la guía docente si vuelve a ocurrir en el aula.
